# API 通知系统 - 需求规格

## 1. 文档目的

本文根据仓库根目录的 `AI Coding 作业.pdf` 拆分题目要求，形成开发、评审和验收时可追踪的功能清单。

标记说明：

- **显式要求**：PDF 直接提出；
- **推导要求**：为满足“稳定、可靠、尽可能可靠投递”而形成的可验证条件；
- **MVP 决策**：当前实现选择，不代表题目限定技术方案。

## 2. 场景与参与者

### 2.1 业务场景

多个企业内部业务系统会在关键事件发生时通知外部供应商，例如：

- 第三方广告引流用户注册成功后通知广告系统；
- 用户订阅付款成功后通知 CRM 更新 Contact 状态；
- 用户购买商品后通知库存系统变更库存。

供应商 API 的请求地址、Header 和 Body 格式不同。业务系统不关心供应商同步返回内容，只需要通知请求能稳定、可靠地送达。

### 2.2 参与者

| 参与者 | 职责 |
|---|---|
| 业务系统 | 构造目标请求并提交给通知服务；必要时使用提交幂等键 |
| 通知服务 API | 校验请求、持久化任务、返回接收结果、提供状态与运维接口 |
| 投递 worker | 异步领取任务、调用供应商、分类结果并更新状态 |
| 外部供应商 | 接收 HTTP(S) 通知；最好按通知 ID 幂等处理 |
| 运维人员 | 观察积压和失败，修复长期问题并重放死信 |

## 3. 功能要求

### FR-01 接收通知请求

**来源：显式要求。**

服务必须接收业务系统提交的外部 HTTP 通知描述，至少能够表达：

- 目标 HTTP(S) URL；
- 不同供应商所需的 Header；
- 不同供应商所需的 Body；
- 投递所需 HTTP method。

当前 MVP 支持 `POST`、`PUT`、`PATCH`，Body 支持任意 JSON 或原始 UTF-8 文本；不支持二进制大文件。

### FR-02 持久化接收

**来源：推导要求。**

通知服务只有在任务已经持久化后才能确认接收。不得仅把任务放入进程内存后返回成功。

当前 MVP 使用 SQLite 事务；成功创建返回 `202 Accepted`。

### FR-03 异步投递

**来源：由“不关心外部 API 返回值”及可靠性目标推导。**

业务提交请求不得等待供应商完成处理。worker 应独立读取已持久化任务并执行外部 HTTP(S) 请求，供应商延迟或故障不应直接传播到业务请求链路。

### FR-04 支持供应商差异

**来源：显式要求。**

服务必须按单条任务保留目标地址、自定义 Header 和 Body，不能把所有供应商绑定到同一种固定 payload。

### FR-05 查询任务状态

**来源：推导要求。**

业务或运维人员必须能够按通知 ID 查询当前状态、尝试次数、下一次尝试时间、最后状态码和失败摘要。查询结果不得返回敏感 Header 或 Body。

### FR-06 查看投递尝试

**来源：推导要求。**

服务应保存每次已确认完成的投递尝试，包括序号、结果、状态码或错误摘要及起止时间，以支持问题定位和审计。

### FR-07 提交幂等

**来源：推导要求。**

业务系统因网络超时重复提交时，可以携带 `Idempotency-Key`。相同 key 应返回已有任务而不是创建新任务。

该能力只避免重复建任务，不代表端到端 exactly-once。

### FR-08 死信人工重放

**来源：由“外部系统长期不可用时的处理策略”推导。**

达到自动尝试上限或遇到永久错误的任务应进入 dead 状态。问题修复后，运维人员能够将 dead 任务重新入队；非 dead 任务不得通过该接口重复入队。

### FR-09 健康检查

**来源：推导要求。**

服务应提供存活检查和包含持久化连接验证的就绪检查，便于部署平台判断是否能够接收流量。

## 4. 可靠性与失败处理要求

### REL-01 投递语义

**来源：PDF 要求明确选择并说明语义；当前选择为 MVP 决策。**

系统采用至少一次投递：已经接受的任务会被持续处理直到成功、被判定为永久失败或达到尝试上限。重复投递是公开契约，不承诺 exactly-once。

### REL-02 原子领取

**来源：推导要求。**

多个 worker 并发时，同一租约周期内只有一个 worker 能领取任务。领取必须通过短数据库事务完成，外部 HTTP 调用不得占用数据库事务。

### REL-03 崩溃恢复

**来源：推导要求。**

领取任务时必须创建有期限的租约。worker 崩溃且租约到期后，任务能够重新被领取，不能永久停留在 `in_flight`。

### REL-04 过期 worker 隔离

**来源：推导要求。**

每次租约必须具有唯一 fencing token。旧租约持有者迟到返回时，不得覆盖新租约持有者的结果。

### REL-05 结果分类

**来源：PDF 要求说明失败处理；具体分类为 MVP 决策。**

| 外调结果 | 预期处理 |
|---|---|
| HTTP 2xx | 标记 succeeded |
| 网络异常、连接或读取超时 | 视为暂时失败并重试 |
| 408、425、429 | 视为暂时失败并重试 |
| HTTP 5xx | 视为暂时失败并重试 |
| 其他 3xx/4xx | 视为永久失败并进入 dead |

重定向不得自动跟随，防止凭据被转发到非预期目标并绕过 allowlist。

### REL-06 退避策略

**来源：推导要求。**

暂时失败必须使用有上限的指数退避和抖动，避免持续攻击不可用供应商或在恢复时形成惊群。供应商提供合法 `Retry-After` 时，应在本地上限内予以尊重。

### REL-07 有界自动尝试

**来源：PDF 要求说明长期不可用策略；当前策略为 MVP 决策。**

自动尝试必须有上限。达到上限后进入 dead 并保留失败信息，不进行无限自动重试；通过告警和人工重放恢复。

### REL-08 重复窗口可见

**来源：推导要求。**

每次外调必须携带稳定的 `X-Notification-Id`，使供应商有能力去重。`X-Notification-Attempt` 仅用于观测。文档必须说明供应商成功与本地落库之间的崩溃窗口。

## 5. 系统边界要求

### BND-01 系统负责

- 可靠接收和持久化通知任务；
- 异步 HTTP(S) 投递；
- 暂时失败重试、永久失败/耗尽转 dead；
- 状态、尝试历史和人工重放；
- 基础输入校验及 SSRF 风险控制。

### BND-02 系统不负责

- 供应商字段映射、业务编排和业务补偿；
- 在不控制供应商事务的情况下提供 exactly-once；
- 全局或实体维度严格投递顺序；
- OAuth 生命周期和任意供应商签名插件；
- 超大文件或二进制 payload；
- MVP 阶段的管理 UI、多租户计费和审批工作流。

以上排除项及原因必须在设计文档说明，满足 PDF 对系统边界判断的要求。

## 6. 安全与运行约束

这些是由“可作为真实内部服务运行”推导的最低要求：

- SEC-01：目标仅允许 HTTP(S)，URL 不得内嵌用户名或密码。
- SEC-02：支持目标 hostname allowlist；未配置时拒绝直接指向私网、回环、链路本地和保留 IP。
- SEC-03：调用方不得控制 hop-by-hop 或传输层 Header。
- SEC-04：限制请求和通知 Body 大小，避免无界内存和数据库增长。
- SEC-05：日志及查询接口不得泄露 Header、Body 或供应商响应 Body。
- SEC-06：MVP 默认绑定 loopback；暴露到共享网络前必须增加 API Gateway/mTLS、身份与租户隔离。
- SEC-07：文档必须披露 DNS rebinding 和凭据明文持久化仍是 MVP 风险，而不是暗示已彻底解决。

## 7. 设计说明要求

以下内容来自 PDF，属于文档必须回答的问题：

### DES-01 系统边界

- 在系统中解决哪些问题？
- 明确不解决哪些问题？为什么？

### DES-02 可靠性与失败处理

- 选择何种投递语义？
- 外部系统失败或长期不可用时如何处理？

### DES-03 取舍与演进

- AI 建议中哪些设计过度，因此未采纳？
- 第一版之后流量或复杂度显著增长时如何演进？
- 判断依据是什么？

### DES-04 中间件选择

如果使用消息队列、数据库调度或其他基础设施，必须说明：

- 为什么选择它；
- 不使用它时的替代方案；
- 它带来的复杂度和适用边界。

当前 MVP 选择 SQLite 租约队列；替代方案及升级触发条件记录在 README。
