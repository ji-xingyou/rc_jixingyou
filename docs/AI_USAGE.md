# AI 使用说明

## AI 提供帮助的关键环节

本作业使用 AI 辅助完成了以下工作：

1. 将题目拆解为接收确认、持久化、异步投递、失败分类、退避重试、死信和重放几个独立问题，并检查设计文档是否逐项回答题目中的系统边界、可靠性、长期失败、取舍和演进问题。
2. 对至少一次、至多一次和“恰好一次”语义进行故障窗口分析，尤其识别“对端成功后、本地成功状态落库前崩溃”这一无法消除的重复窗口。
3. 生成代码骨架、SQLite schema 和基础测试，再通过人工审阅收紧模块边界、输入校验、敏感信息输出和错误分类。
4. 列出潜在失败场景（429、5xx、连接超时、进程崩溃、任务永久失败、重复提交），据此补充测试和运维接口。
5. 辅助整理 README 的可运行说明、架构描述、生产风险和演进触发条件。

AI 主要承担“扩展候选方案、提醒遗漏、生成机械性代码”的角色；可靠性承诺与复杂度边界由人工决定，并以可测试的状态机为准。

## AI 建议但没有采纳的内容

| 未采纳建议 | 不采纳原因 |
|---|---|
| 一开始引入 Kafka/RabbitMQ + Redis + PostgreSQL | 对单机 MVP 造成三套基础设施和双写/运维问题，掩盖核心判断。当前 SQLite 事务队列足以验证语义。 |
| 使用 Celery/FastAPI/SQLAlchemy | 框架本身合理，但为很小的服务增加依赖、配置和抽象层；标准库可以保持仓库克隆即跑，并让租约和事务语义显式可见。 |
| 无限重试以追求“最终一定送达” | 无效请求或永久下线目标会无限占用容量。采用有界重试 + dead + 告警 + 人工重放。 |
| 对所有 4xx 都重试 | 大多数 4xx 是请求或鉴权的永久问题；只对 408/425/429 重试，避免无意义流量。 |
| 自动跟随 HTTP 重定向 | 可能把带 Authorization 的请求转发到非预期主机，也使 allowlist 失效；将 3xx 视作需人工修复的永久失败。 |
| 在 v1 实现严格顺序、优先级、熔断、管理后台和多租户 RBAC | 都有合理场景，但题目要求 MVP；这些能力会改变状态机或运维模型，应由真实需求和指标触发。 |
| 宣称通过幂等键实现 exactly-once | 提交幂等只能防止调用方重复建任务，不能消除外调成功与本地落库之间的重复窗口。 |

## 人工做出的关键决策

1. **选择至少一次而非虚假的恰好一次。** 原因是外部 HTTP 系统不参与本地事务；诚实暴露重复可能性，并提供稳定通知 ID，是可落地的接口契约。
2. **以持久化成功作为 `202` 的边界。** 只有 SQLite 事务提交后才确认，避免“返回成功但进程退出后任务丢失”。
3. **MVP 使用 SQLite 租约队列。** 这是对交付速度、可运行性、可靠性展示和运维成本的平衡，不代表它适合所有规模。
4. **将外部调用放在事务之外。** 长网络调用不能占用数据库写锁；领取靠短事务和租约，完成再用短事务更新。
5. **有界退避后进入 dead。** “可靠”不等于无限重试，而是失败可见、可审计、可恢复。
6. **安全默认优先于任意 URL 的便利。** 加入 host allowlist 能力、危险 Header 拒绝、重定向禁用和响应体上限；同时明确 MVP 对 DNS rebinding 和凭据静态存储的不足。
7. **不把供应商适配逻辑放入投递核心。** 本服务保持传输层职责；字段映射、业务规则、OAuth 生命周期属于另一个边界。

## 对 AI 输出的验证与修正方式

- 逐条回看原始 PDF，将每个显式问题映射到 README 章节。
- 用状态机检查每条转移是否有持久化落点，确认崩溃后的恢复路径。
- 用单元测试验证提交幂等、领取互斥及成功/永久失败/暂时失败三条核心路径。
- 运行 Python 编译检查，避免仅凭 AI 判断代码可运行。
- 人工审阅日志和查询返回，确保不会直接泄露 Header/Body。
